    Steps glossary

    Explains the steps that perform several checks internally. Steps that do a single, self-explanatory action are intentionally left out.

    Given

    a complex debt position with {po_size} payment options created by organization interacting with {pagopa_interaction}

    also: a debt position {dp_identifier} with {po_size} payment option and {installments_size} installments created by organization interacting with {pagopa_interaction}

    Creates a complex debt position (several payment options with installments) in one step. It:

    • gets the organization token and builds the payment options;
    • creates the debt position and checks it becomes UNPAID;
    • verifies presence in the GPD/ACA archive and the scheduled expiration workflow.

    a mixed debt position created by SIL for organization interacting with {pagopa_interaction} configured as follows

    Creates a mixed debt position via SIL in one step. It:

    • gets the SIL token and builds the mixed entity;
    • sends it through SIL and retrieves the resulting debt positions by IUV;
    • validates all data of generated debt positions (status, amounts, expiration workflow, ecc);
    • verifies presence as valid in the GPD/ACA archive.

    a notification created for the single installment of debt position {dp_identifiers}

    also: a notification created for the single installment of debt positions {dp_identifiers}, a notification created for the {installments_size} installments of debt positions {dp_identifiers}

    Creates a SEND notification for the selected installments. It:

    • builds the notification request (recipients and pagoPA payments) for the given debt positions;
    • gets a SEND token and posts the notification;
    • asserts the call succeeds and the notification is created in status WAITING.

    a payment reporting with outcome code 9 has been successfully processed for the installment created outside PU

    For a debt position created outside PU, uploads a payment reporting with outcome code 9 and checks, in one step, that it is processed and that the debt position is created correctly.

    a payment reporting with outcome code {outcome_code} has been successfully processed for the installment

    Uploads a payment reporting and checks it is processed, in one step:

    • uploads the file,
    • checks the debt position becomes REPORTED,
    • checks processing and (for outcome 9) that the receipt is created.

    a simple debt position created by organization interacting with {pagopa_interaction}

    also: a simple debt position of type {dp_type_org_code} created by organization interacting with {pagopa_interaction}, a simple debt position {dp_identifier} for citizen {citizen_identifier} created by organization interacting with {pagopa_interaction}

    Creates a simple, single-installment debt position in one step. It:

    • gets the organization token and builds the debt position entity;
    • creates it and checks it becomes UNPAID;
    • verifies the notice is present as valid in the GPD/ACA archive;
    • checks the expiration workflow is scheduled.

    a simple debt position created on {pagopa_interaction}

    Creates a simple debt position directly on GPD/ACA (bypassing PU creation):

    • builds the entity and its transfer, generating IUV/NAV/IUPD;
    • posts it to GPD/ACA and asserts the call succeeds;
    • verifies the notice is present as VALID in the GPD/ACA archive.

    a simple debt position with balance created by organization interacting with {pagopa_interaction}

    Like a simple debt position created by organization..., but with a balance set to the installment; creates it and checks UNPAID status, presence in GPD/ACA and the scheduled expiration workflow.

    the previous payment of installment {seq_num} of payment option {po_index}

    Given that plays a full payment-and-reporting cycle for one installment and checks the outcome:

    • pays the installment and checks the receipt is processed;
    • checks the other payment options become INVALID;
    • uploads the payment reporting and checks the installment becomes REPORTED;
    • uploads the treasury file and checks it is processed;
    • checks the payment option and debt position become PARTIALLY_PAID;
    • checks the resulting classification labels.

    the successful payment of the installment

    Performs a full successful payment in one step:

    • pays the installment,
    • checks the debt position becomes PAID
    • checks the receipt is processed correctly.

    the successful payment of the installment created outside PU

    Like the successful payment of the installment, but pays the first installment of a debt position created outside PU, then checks the PAID status and that the receipt is processed.

    When

    SIL creates the mixed debt position

    Creates the mixed debt position through SIL (paaSILInviaDovuti) and asserts the SOAP outcome is OK with a URL to proceed for payment.

    the citizen pays the installment of payment option {po_index}

    also: the citizen pays the installment {seq_num} of payment option {po_index}, the citizen {citizen_identifier} pays the installment of debt position {dp_identifier}, the citizen pays the installment {seq_num} of debt position {dp_identifier}

    Simulates the citizen paying the installment through the pagoPA node. It:

    • verifies the payment notice (verifyPaymentNotice) and reads amount/due date;
    • activates the payment notice (activatePaymentNotice) and gets a payment token;
    • sends the payment outcome (sendPaymentOutcome), each call expected to return OK

    the organization creates the debt position

    Creates the debt position and validates the outcome. It:

    • posts the debt position and asserts the call succeeds;
    • validates the whole created structure (payment options, installments, first transfer) in TO_SYNC;
    • checks the organization's sync workflow (ACA/GPD) completes.

    the organization requires the notification to be uploaded to SEND

    Uploads the notification and payment PDFs to SEND. It:

    • uploads the notification file and one payment file per notified installment;
    • reads the workflow id from the last upload;
    • checks the notification moves to IN_VALIDATION with no IUN yet;
    • waits for the upload workflow to complete.

    Then

    3 debt positions having installments with same IUV are in status {status} configured as follows

    Checks the debt positions generated from a mixed SIL flow (sharing the same IUV). For each configured row it:

    • looks up the spontaneous-mixed or spontaneous-SIL debt position and asserts they exist as configured;
    • validates their status, amounts, payment option and installments/transfers against the request.

    SEND has set a notification fee

    Checks that SEND set a notification fee: reads the fee for each notified installment, asserts it is present and that all installments share the same fee.

    the amount of installment of debt position {dp_identifier} is increased by the notification fee

    also: the amount of installment {seq_num} of debt position {dp_identifier} is increased by the notification fee

    Checks that the notified installment's amount was increased by the notification fee (both notificationFeeCents and amountCents).

    the assessment classification label for each IUD is {label}

    Checks the assessment-detail classification labels for a mixed debt position. It:

    • asserts the debt position with type ord MIXED has no assessment details/classification;
    • for each mixed transfer, checks the CLASSIFY_ASSESSMENT workflow completes;
    • verifies one assessment detail per balance section, each with the expected IUR, type org code and label.

    the assessment detail is created correctly based on balance

    also: the assessment detail is created correctly based on balance including {dptobc_type} section

    Checks that assessment details were created from the balance. It:

    • retrieves the expected balance sections (optionally including a given DPTOBC section);
    • checks the CLASSIFY_ASSESSMENT workflow completes;
    • verifies one assessment detail per section with matching IUR, PAID label, amount and registry codes.

    the assessment is in status {status}

    also: the assessment related to debt position {dp_identifier} is in status {status}

    Checks that the assessment for the paid installment is in the expected status. It:

    • reads the installment and its sourceFlowName;
    • fetches the assessment by that name and asserts it exists and matches the status;
    • checks the CREATE_ASSESSMENT workflow completes.

    the classification labels are {labels}

    also: the classification labels for each transfer are {labels}, the classification labels related to payment reporting with outcome code {outcome_code} are {labels}

    Checks the classification labels produced for the installment. It:

    • queries the classifications for today by IUV (and by IUF/IUR when payment reporting with outcome code specified is uploaded);
    • asserts at least one classification exists;
    • verifies that, for every transfer, the stored labels match the expected set.

    the debt position is created correctly

    Checks that the debt position was created correctly. It:

    • looks it up by NAV and asserts exactly one is found;
    • verifies its origin and, for receipt-file origin, that it is PAID;
    • checks the installment IUV and, for pagopa-reporting origin, the outcome-9 remittance and anonymous debtor.

    the debt positions are created correctly with origin {debt_position_origin}

    Runs the the debt position is created correctly checks for every debt position imported from file.

    the debt positions {identifiers} are created in status {status}

    Checks that the debt positions imported from the file were created in the expected status:

    • fetches the debt positions by ingestion-flow id and asserts the count matches the identifiers;
    • validates each created debt position against its request (fields, payment options, installments).

    the duplicate receipt for the payment reporting with outcome code {outcome_code} is created correctly with origin {receipt_origin}

    Checks that the duplicate receipt for the given payment-reporting flow (by outcome code) is created with the expected origin.

    the ingestion file is processed correctly

    Checks that the debt-positions ingestion file was processed correctly. It verifies that:

    • the file reaches COMPLETED (or WARNING when the organization has no generate-notice API key);
    • the number of imported rows equals the rows sent and all were imported successfully;
    • the DEBT_POSITION_INGESTION_FLOW workflow completes.

    the mixed debt position and technical ones are in status {status}

    Checks that the mixed debt position and its technical (spontaneous-mixed) ones are all in the expected status.

    the notification is in status {status} and the IUN is assigned to the installment

    also: the notification is in status {status} and the IUN is assigned to all installments

    Checks that the notification is valid and the IUN is assigned. It:

    • polls SEND until the notification is valid and asserts it has an IUN;
    • verifies that every notified installment carries that same IUN.

    the payment reporting is processed correctly

    Checks that the payment reporting file was processed correctly. It verifies that:

    • the file reaches status COMPLETED;
    • the PAYMENTS_REPORTING_INGESTION workflow completes;
    • the TRANSFER_CLASSIFICATION workflow completes for each transfer;
    • the installment now has its IUF set.

    the payment reporting with outcome code 9 is processed correctly

    Checks that a payment reporting with outcome code 9 was processed correctly. It verifies that:

    • the file reaches status COMPLETED;
    • the PAYMENTS_REPORTING_INGESTION workflow completes;
    • the TRANSFER_CLASSIFICATION workflow completes.

    the receipt is created correctly with origin {receipt_origin}

    Checks that the receipt for the paid installment was created with the expected origin. It verifies that:

    • the receipt exists (looked up by IUV/IUR, or by IUR when it is a duplicate);
    • its receiptOrigin matches the expected one and it is linked to the installment (receiptId);
    • the TRANSFER_CLASSIFICATION workflow completes for each transfer;
    • the IUD_CLASSIFICATION workflow completes.

    the receipt is processed correctly

    also: the receipt of debt position {dp_identifier} is processed correctly

    Checks that the pagoPA receipt has been fully processed. It verifies that:

    • the receipt file RT_<nav>.xml reaches status COMPLETED;
    • the paid installment now has both IUR and receiptId set;
    • the async TRANSFER_CLASSIFICATION workflow completes;
    • the async IUD_CLASSIFICATION workflow completes.

    the receipts are created correctly with origin {receipt_origin}

    Runs the the receipt is created correctly checks for every receipt imported from the file.

    the receipts file is processed correctly

    Checks that the receipts file was processed correctly. It verifies that:

    • the file reaches status COMPLETED;
    • the number of imported rows equals the rows sent and all were imported successfully;
    • the RECEIPT_INGESTION_FLOW workflow completes.

    the treasury is processed correctly

    Checks that the treasury OPI file was processed correctly. It verifies that:

    • the file reaches status COMPLETED;
    • the TREASURY_OPI_INGESTION workflow completes;
    • the TRANSFER_CLASSIFICATION workflow completes for each transfer;
    • the IUF_CLASSIFICATION workflow completes.
