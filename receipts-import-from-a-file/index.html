    Scenario: A receipt imported from a file for a debt position in PU is updated by importing it again with modified data and balance

    Tags: @receipts_file_update

    Given a simple debt position created by organization interacting with GPD
# (1)!
And a receipt successfully imported from a receipts file with version 1_3
# (2)!
When the same receipt with amount increased by 20 euros, modified remittance information and balance is inserted into an ingestion flow file with version 1_3
# (3)!
And the organization uploads the receipts file
Then the receipt is imported correctly and the debt position is paid
# (4)!
And the receipt is updated
# (5)!
And the installment keeps its original amount
And the assessment details are recalculated
# (6)!
And the assessment detail is created correctly based on balance
# (7)!

    1. Creates a simple, single-installment debt position in one step. It:

      • gets the organization token and builds the debt position entity;
      • creates it and checks it becomes UNPAID;
      • verifies the notice is present as valid in the GPD/ACA archive;
      • checks the expiration workflow is scheduled.

    2. Imports a receipt from a receipts file and checks it is processed:

      • builds the receipts file and uploads it
      • checks that the receipts file is processed
      • checks that the receipt is created with origin RECEIPT_FILE
      • checks that the installment of payment option 1 and the debt position are PAID
      • checks that the assessment is CLOSED and its details match the balance

    3. Builds a receipts file containing the receipt already imported, with modified data. It:

      • keeps the same receipt identifier, IUV and IUD, so that the existing receipt is updated
      • changes the remittance information, increases the amount by the given value and changes the balance using different assessment codes so that the recalculated assessment details differ from the previous ones

    4. Checks that the uploaded receipt is imported for the debt position. It verifies that:

      • the receipts file is processed
      • the receipt is created with origin RECEIPT_FILE
      • the installment of payment option 1 and the debt position are PAID

    5. Checks that the receipt already imported has been updated by the last receipts file. It verifies that:

      • there is still exactly one receipt linked to the installment for the IUV and IUR
      • the receipt refers to the last ingestion flow file and has the modified remittance information and amount

    6. Checks that the assessment workflows ran again after the last receipts file. It verifies that a new run of the CREATE_ASSESSMENT and of the CLASSIFY_ASSESSMENT workflows completes

    7. Checks that assessment details were created from the balance. It:

      • retrieves the expected balance sections (optionally including a given DPTOBC section);
      • checks the CLASSIFY_ASSESSMENT workflow completes;
      • verifies one assessment detail per section with matching IUR, PAID label, amount and registry codes.

    Scenario: An installment paid by a receipt imported from a file is linked to the receipt sent by pagoPA node

    Tags: @receipts_file_update

    Given a simple debt position created by organization interacting with GPD
# (1)!
And a receipt successfully imported from a receipts file with version 1_3
# (2)!
When the citizen pays the installment
# (3)!
Then the receipt is processed correctly
# (4)!
And the receipt is created correctly with origin receipt_pagopa
# (5)!
And the installment is linked to the pagoPA receipt
# (6)!

    1. Creates a simple, single-installment debt position in one step. It:

      • gets the organization token and builds the debt position entity;
      • creates it and checks it becomes UNPAID;
      • verifies the notice is present as valid in the GPD/ACA archive;
      • checks the expiration workflow is scheduled.

    2. Imports a receipt from a receipts file and checks it is processed:

      • builds the receipts file and uploads it
      • checks that the receipts file is processed
      • checks that the receipt is created with origin RECEIPT_FILE
      • checks that the installment of payment option 1 and the debt position are PAID
      • checks that the assessment is CLOSED and its details match the balance

    3. Simulates the citizen paying the installment through the pagoPA node. It:

      • verifies the payment notice (verifyPaymentNotice) and reads amount/due date;
      • activates the payment notice (activatePaymentNotice) and gets a payment token;
      • sends the payment outcome (sendPaymentOutcome), each call expected to return OK

    4. Checks that the pagoPA receipt has been fully processed. It verifies that:

      • the receipt file RT_<nav>.xml reaches status COMPLETED;
      • the paid installment now has both IUR and receiptId set;
      • the async TRANSFER_CLASSIFICATION workflow completes;
      • the async IUD_CLASSIFICATION workflow completes.

    5. Checks that the receipt for the paid installment was created with the expected origin. It verifies that:

      • the receipt exists (looked up by IUV/IUR, or by IUR when it is a duplicate);
      • its receiptOrigin matches the expected one and it is linked to the installment (receiptId);
      • the TRANSFER_CLASSIFICATION workflow completes for each transfer;
      • the IUD_CLASSIFICATION workflow completes.

    6. Checks that the installment is linked to the receipt sent by pagoPA instead of the one imported from file. It verifies that:

      • the installment IUR isn't the one imported from file
      • the receipt linked to the installment has origin RECEIPT_PAGOPA and the same IUR of the installment
